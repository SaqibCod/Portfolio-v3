## Overview

Medi-Scan explains a lab report in plain language. You upload it as a PDF, a photo or pasted
text — or pick one of three synthetic samples — and it reads every value, checks each one
against the reference range **printed on that report**, flags it LOW, NORMAL or HIGH, and
writes a summary at roughly a sixth-grade reading level. Then you can ask questions about it in
a chat.

The point of the project is not the chatbot. It is that the AI pipeline is measured, private
and bounded: a model never decides a number, nothing unmasked reaches the model, and the whole
thing runs on free tiers under a hard $0 ceiling.

Medi-Scan explains what a report says. It is not medical advice and it does not diagnose.

## The problem

A lab report is a table of numbers written for someone who already knows what they mean. The
patient holding it gets a column of values, a reference range in small print, and no
explanation — so "LDL 162 mg/dL, range &lt;100" turns into a search engine and an afternoon of
worry, or a wait of several days to ask a doctor.

Pasting it into a general chatbot replaces that with three worse problems:

1. **It can be confidently wrong.** It misreads a digit, or decides a value is high using its
   own idea of "normal" rather than the range on the page.
2. **It is a privacy hole.** Reports carry names, patient IDs, phone numbers and dates of
   birth.
3. **It drifts into diagnosis.** Asked "is this serious?", a general model answers.

Every design decision below exists because of one of those three.

## Architecture

The browser uploads a report and gets an id immediately, then polls for status while a
background worker runs the pipeline: extract text, mask personal data, ask the model for the
printed strings, verify and compute the flags **in code**, then ask the model a second time for
the summary. Only masked text ever reaches the model or the database; raw text stays in memory
and is discarded.

The verification step is the whole design in one rule: a value the model returns has to appear
word-for-word in the extracted text, or it is dropped.

<CodeBlock
  filename="Verification rule"
  code={`// The model is asked only for strings exactly as printed.
// Code parses them, checks them against the source, and decides the flag.
var verified = extracted.stream()
    .filter(row -> reportText.contains(row.rawValue()))
    .map(row -> flagger.flag(row, Range.parse(row.rawRange())))
    .toList();`}

## Challenges & results

An evaluation set is what turns "it seems to work" into numbers: roughly 31 synthetic reports
with hand-written answer keys, plus photo and scanned versions, plus about 40 chat questions. It
scores extraction accuracy, flag correctness, dangerous flag errors, personal-data leaks,
invented numbers and correct refusals. Responses are cached on disk so re-scoring after a code
change costs no API calls — which is what makes measuring affordable on a free tier.

Measured results are pending the final evaluation run: extraction recall and precision, flag
accuracy, dangerous flag errors (target 0), personal-data leaks (target 0), invented numbers in
chat (target 0) and correct refusals (target 100%). Street addresses are a known masking gap and
are reported as such rather than quietly omitted. The suites behind it are large — the client
tests alone number 450+ — and the accessibility pass targets WCAG 2.2 AA.
