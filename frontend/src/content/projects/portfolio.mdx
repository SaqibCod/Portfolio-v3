## Overview

Two halves. A Next.js frontend renders every page that matters for search at
build time, so the content is in the HTML before any JavaScript runs. A Spring
Boot API handles only what genuinely has to be live: the AI chat, GitHub stats,
uptime history, a moderated guestbook, the contact form and live presence.

For the full walk-through of how a request flows through both halves, see
[Tech behind this site](/tech).

## The problem

A portfolio has two jobs that pull in opposite directions. It has to be fully
readable by a crawler and fast on a cold load, and it has to show that the
person who built it can do real backend work. Making everything dynamic fails
the first job; making everything static fails the second.

So the split is the point: nothing that a crawler needs is ever behind a fetch,
and nothing that is genuinely live pretends to be static.

## Architecture

Pages are pre-rendered by Next.js and served as HTML. Each live widget calls
one versioned endpoint under `/api/v1` after the page has painted, so a slow or
unavailable API degrades a single card rather than the page. Errors are
RFC 9457 Problem Details everywhere, and nothing public requires an account.
